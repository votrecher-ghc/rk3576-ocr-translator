本文记录 `IMPLEMENTATION_GUIDE.md` 续作后的真实交付边界。软件主链已经从骨架补齐为可执行实现，但目标机交叉编译、模型数值验证和硬件联调必须在野火 RK3576 SDK 与实板上完成；未经过这些步骤前，不应标记为量产验收通过。

## 已完成的软件闭环

- V4L2 MMAP + DMA-BUF 导出、按索引缓冲池、引用归还后 QBUF、异常帧丢弃与采集停滞退出。
- 带 stride/offset 的 DMA-BUF 图像描述、16 像素对齐 DMA-HEAP 输出、RGA resize/crop/format 路径。
- DRM connector/CRTC/plane 筛选、同步 page-flip 完成事件、视频帧持有、双缓冲文字 overlay 和退出状态恢复。
- RKNN 模型加载、张量契约校验、OCR 检测/旋转四点框/透视识别/UTF-8 CTC，以及严格的静态 encoder/decoder 翻译契约。
- 实时与拍照模式互斥使用 RKNN 上下文，拍照 JPEG/OCR 的 DMA CPU 同步区间配平。
- ICM42688 数据就绪中断/IIO triggered buffer、用户态 scan layout 发现与姿态融合，以及裁剪/平移防抖。
- AP3216C Rev0.86 寄存器表、10-bit PS/IR overflow 与 0.35 lux/count IIO scale，以及 ADT7410 精确毫摄氏度 raw/scale/offset/processed ABI。
- 按 IIO `name` 与 `KEY_CAMERA` 能力自动发现传感器/按键；光照背光、用户态独占 PWM 温控、归档与锚定目录清理。
- 生产源码链接的 ringbuffer、msgbus、event loop、buffer/pool、config、pipeline 和 OCR 后处理测试。
- Vendor Buildroot external tree、模型/词表/字体完整性与 SHA256 校验、DT overlay 单一路径打包，以及无危险默认块设备的烧录入口。

## 必须在目标板闭环的项目

| 项目 | 当前边界 | 通过条件 |
|---|---|---|
| SDK 交叉编译 | 本工作环境没有 RK3576 sysroot、librga、librknnrt 和交叉编译器 | 使用目标镜像同源 SDK 完成全量编译，`-Wall -Wextra` 无新增告警 |
| 自研内核驱动与 IMU 缓冲 | AP3216C/ADT7410 的寄存器与 IIO 单位、ICM42688 的寄存器/量程/1kHz IRQ trigger 和 24-byte 缓冲帧布局已按 Linux 6.1 接口实现，但本机没有 vendor 内核树可编译 | 在同源 kernel 6.1 中构建全部模块；验证 AP 光照/PS overflow、ADT 正负温度、ICM WHO_AM_I/DRDY IRQ/固定 scan mask/时间戳及 1kHz 连续采样 |
| 设备发现与 PWM 所有权 | 运行时不再假定 `iio:device0`/`event0`；按 IIO 名称及按键能力发现。风扇由应用直接拥有 PWM sysfs，默认 DTS 不绑定可选的内核风扇驱动；固定进程锁阻止并发接管，auto 模式会清理崩溃遗留的专用导出 | 核对三个 IIO 名称、`KEY_CAMERA`、实际 `pwmchip/channel` 和极性；确认同一 PWM 没有第二个 consumer，进程启动/并发启动/异常退出/重启均能恢复安全状态 |
| DTS/引脚与启用路径 | overlay 中的 I2C/SPI/GPIO/CSI 节点和供电名称仍需与实际鲁班猫3底板核对；打包/TFTP 默认只用 base DTB。`merged` 与 `vendor-resource` 是互斥启用路径 | `dtc`/内核构建通过，逐项核对原理图和 base DTS；每次构建只选一种 overlay 启用模式，启动无重复节点、资源冲突或 deferred probe |
| 摄像头媒体图 | 应用支持单平面或单连续 DMA 平面的 V4L2；不支持多个独立 DMA plane 或非零 data offset。未核对的 IMX415 overlay 默认不构建 | 以出厂 DTS/media graph 为基线，`media-ctl -p` 链路正确，目标格式连续输出，错误帧/断流恢复策略验证通过 |
| 任意角防抖 | librga `imrotate` 只提供 90/180/270 度；当前 roll 用裁剪/平移包络近似 | 若产品要求真实 roll 校正，接入 RK3576 可用的仿射/透视硬件路径并做画质、延迟测试 |
| JPEG 性能 | 拍照功能当前使用 libjpeg CPU 编码，结果正确但不是 MPP 零拷贝硬编 | 接入与 vendor MPP 版本匹配的 DMA-BUF JPEG 编码后，验证码流与错误回收 |
| 模型资产与兼容性 | 仓库不包含可分发的 ONNX/RKNN、词表或量化图片；转换入口会生成并由 rootfs 构建验证 `model_artifacts.sha256`。翻译只接受项目专用 `greedy-vocab-v1` 静态双模型接口 | 固定 RKNN Toolkit2、板端驱动/运行时版本和资产来源；真实词表/manifest 的 SHA256 验证通过，跑 golden vectors，目标板输出与 PC 基线一致 |
| 实时性能 | OCR 图像预处理仍有 CPU fallback，识别逐框、翻译逐 token | 30 分钟稳态测试无泄漏/冻屏，按产品目标记录 FPS、P95 延迟、NPU/RGA/CPU 利用率 |
| 多屏 KMS | 已避免抢占其他 CRTC 的活动 plane，并保留克隆 connector；仍需验证目标 DRM 驱动行为 | `modetest` 核对 plane 格式/zpos/blend，启动退出前后拓扑一致且无撕裂 |
| 完整固件打包 | 项目只安全生成分区镜像；不使用 `upgrade_tool pack` 冒充 vendor 打包流程 | 设置 `RK_PACK_SCRIPT`，用实际 SDK 的 parameter/MiniLoader/afptool/rkImageMaker 生成并回读验证 update.img |

## 建议验收顺序

1. 在普通 Linux 主机执行硬件无关测试：

   ```bash
   cmake -S app -B output/test-build \
     -DOCR_BUILD_HARDWARE_APP=OFF -DBUILD_TESTING=ON
   cmake --build output/test-build --parallel
   ctest --test-dir output/test-build --output-on-failure
   ```

2. 使用与板端 rootfs 同源的 vendor SDK 交叉编译应用，再构建模型和 rootfs。不要用上游 Buildroot 替代带 Rockchip RGA/RKNN 包的 vendor tree。
3. 先验证 DRM/V4L2/RGA/传感器单项，再启动 `ocr_translator`；确认日志中的实际 stride、格式、模型 I/O shape 与配置一致。
4. 分别运行 live/photo 模式，注入断摄像头、错误帧、模型缺失、磁盘高水位和 SIGTERM，确认进程明确失败或完整回收。
5. 最后执行长稳、温升、掉电归档一致性和语言 golden-vector 测试，并把结果填写到 `07-测试报告模板.md`。
